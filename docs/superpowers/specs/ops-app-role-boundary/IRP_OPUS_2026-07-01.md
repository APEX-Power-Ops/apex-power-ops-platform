# Claude-side IRP Review Record: ops_app Role-Boundary Spec (pre-build security packet)

## 1. Verdict
READY_WITH_FIXES: the boundary design is sound and no finding invalidates it, but the migration and test-cutover wiring is broken as authored (one CRITICAL that hard-fails the ladder, two CRITICAL/HIGH that make the "AS ops_app" proof unrunnable or false-green) and must be fixed before build.

## 2. Convergence (where the lenses agreed the spec is sound)
- The privilege boundary itself holds. grant-matrix-completeness and boundary-integrity independently confirmed, against the live ops_dev catalog, that: every DML the ops-intake package issues maps to exactly one matrix row; the 9-function SECURITY DEFINER set is complete (only writers of the ledger/attestation/apparatus.status are those 9, all others are table-DML triggers); apparatus.status is unreachable by ops_app so governed-complete (status=Complete AND provenance_status=approved) is unforgeable at the privilege layer; the freeze guard and completion guard cannot be bypassed via the granted column UPDATEs; the two EXECUTE-granted recognition fns derive amount/status from persisted row state, never from caller args (no definer-side forgery); and the REVOKE-EXECUTE-FROM-PUBLIC-before-DEFINER-conversion ordering is correctly specified and load-bearing.
- The grant matrix vs approve.py/load.py column set is internally coherent (cutover-test-honesty agreed the defect is entirely in the cutover/test wiring, not the matrix).
- View-security branch R2 resolves in the spec's favor: all 11 ops views are postgres-owned and non-security_invoker, so the "(none)" base-table rows (completion_attestation, billing_*) are safe from view-expansion.
- The 4 FOR UPDATE sites, the scopes-DELETE RI cascade (children run as constraint owner), and the deferred-EXECUTE-for-billing decision are all correctly dispositioned.
- Individually correct migration mechanics: the role-guard DO block, ALTER FUNCTION-based DEFINER conversion/revert, REVOKE CONNECT intent, and the negative column-privilege asserts.

## 3. CONFIRMED findings by severity (each with evidence + fix)

### CRITICAL
- **[migration] Migration 012 references schema `work`, which the ops ladder never creates -> 012 hard-fails on ops_test.** Evidence: grep of migrations/ops/*.sql shows the only `create schema` statements are ops (001:11, 004:13) and core (008:9); ops_test rebuilds to ops+core only; live-proven `revoke execute on all functions in schema work from public` errors `schema "work" does not exist` on ops_test (work exists on ops_dev only, out-of-band). This is AC#2 / GATE-6; 012 cannot apply, so every downstream proof fails before any grant is tested. Fix: presence-gate every `work` reference (REVOKE, ALTER DEFAULT PRIVILEGES, negative assert loop) on `IF EXISTS (SELECT 1 FROM pg_namespace WHERE nspname='work')`; treat schema-absent as pass.
- **[cutover] A single OPS_DEV_DSN feeds both admin fixtures and the app-under-test; no fixture-level split is specified.** Evidence: control-plane routers hardcode os.environ['OPS_DEV_DSN'] (intake_router.py:53, recognition_router.py:24) while the apply_migrations ladder, person setup INSERT, and autouse TRUNCATE read the same var (test_ops_intake_routes.py:63-64,80,116,149). Set it to ops_app -> autouse fixtures raise permission-denied and the suite errors; leave it admin -> behavior runs as superuser and AC5's EXECUTE/GRANT proof is a false-green. AC5/AC6 unmeetable as the harnesses exist. Fix: split at the fixture level - app/behavior reads the ops_app DSN; ALL admin fixtures (ladder, clean_ops/clean_ops_between_tests TRUNCATE, person/eligible setup INSERTs) read a distinct OPS_DEV_ADMIN_DSN and open their own admin connections; enumerate every fixture that must flip, as concrete conftest-edit tasks.
- **[cutover] Recognition-behavior test setup does status writes ops_app is denied, breaking the positive-pipeline-AS-ops_app proof.** Evidence: _eligible() names status on the apparatus INSERT (test_recognition_wrappers.py:19-21; test_ops_recognition_routes.py:47-48) and test_recognize_without_attestation does SET LOCAL ops.completion_ctx='1'; UPDATE ops.apparatus SET status='Complete' (lines 62-65); ops_app holds no status INSERT/UPDATE (D2 / Section 4). All run through the single clean_ops dsn shared with the behavior, so there is no setup-vs-behavior connection split. NOTE (adjudication correction): the finding's secondary claim that "ops_app has no source privilege" is WRONG - the matrix grants apparatus INSERT on all load.py cols EXCEPT status, and load.py's INSERT includes source, so source-INSERT IS held; the denial is status-only. Severity unchanged (status denial alone breaks setup). Fix: two-connection pattern - precondition/setup helpers (_person, _eligible, forced-Complete) open an admin connection; the behavior calls (recognition wrappers, approve_run) open the ops_app connection; refactor those helpers to take an explicit admin DSN.

### HIGH
- **[migration] `ALTER DEFAULT PRIVILEGES ... REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC` is a silent no-op for functions -> audit gap G-A is NOT closed.** Evidence: live-reproduced on ops_dev in a rolled-back txn - after the ADP, a freshly created ops function still returns has_function_privilege('public',...,'EXECUTE')=t with pg_default_acl empty (EXECUTE-to-PUBLIC is a hard-wired world default ADP cannot displace); only the explicit `REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA ops FROM PUBLIC` works. Any future ops function silently re-acquires PUBLIC EXECUTE, reopening the DEFINER escalation class. Fix: do not rely on ADP for functions; keep the explicit ALL-FUNCTIONS REVOKE, add a standing CI convention that every new ops function carries an explicit REVOKE, and add a posture assert that FAILS if any ops function has PUBLIC EXECUTE post-migration.
- **[migration] DSN cutover breaks the DDL ladder: test_00x/012 read OPS_DEV_DSN to run CREATE SCHEMA/function DDL; rotating it to ops_app runs the ladder as a non-superuser and fails.** Evidence: test_001..011 all read OPS_DEV_DSN through autocommit _exec running the raw DDL chain; no conftest.py exists under migrations/ops/ to indirect. Post-swap the ladder runs as ops_app (NOSUPERUSER, owns nothing) and errors on CREATE SCHEMA/function; if left as postgres for tests, boundary proofs false-green. Fix: explicitly repoint the DDL ladder + TRUNCATE fixtures in every test_00x/012 to OPS_DEV_ADMIN_DSN and route only behavior/boundary connections to the ops_app DSN, as a file-by-file Section-7 checklist item. Also fix the dead conftest fallback.
- **[cutover] Autouse TRUNCATE fixtures need TRUNCATE privilege ops_app is never granted.** Evidence: clean_ops (conftest.py:44-49) and clean_ops_between_tests (test_ops_intake_routes.py:143-150) execute _OPS_TRUNCATE over ops.* via OPS_DEV_DSN; TRUNCATE is a distinct PG privilege not implied by DELETE, and the matrix grants none. Once OPS_DEV_DSN is ops_app every autouse TRUNCATE fails before any assertion. Fix: require these named fixtures to connect via OPS_DEV_ADMIN_DSN; list them by name in the cutover checklist as fixtures that must NOT rotate to ops_app. (Strict subset of the CRITICAL fixture-split defect.)

### MEDIUM
- **[concurrency] The Task-0 FAIL bounded fallback mischaracterizes the apparatus row-lock as belt-and-suspenders; dropping it removes the ONLY cross-path serialization between approve_run full-replacement and a concurrent Chip-3 approve_and_recognize.** Evidence: approve_run's advisory lock is on hashtext(project_number) (approve.py:186), held only by intake writers; approve_and_recognize takes NO advisory lock and serializes purely via `for update of a2` (005:89); approve.py:230-232 states verbatim the apparatus lock exists to serialize approve_and_recognize; intake_runs/projects FOR UPDATE do not cover it. The spec's re-proof obligation names only "two concurrent approves of the same project_number" - a race the advisory lock already covers. ADJUDICATION (HIGH->MEDIUM): the finding overstated the consequence as silent revenue corruption; the schema backstops it fail-closed - revenue_recognition_event.apparatus_id -> ops.apparatus is NO ACTION (confdeltype='a') and reinserted apparatus get fresh UUIDs, so a committed recognition event makes approve_run's cascade DELETE ABORT the whole txn rather than corrupt. Worst case is fail-closed, not corruption -> MEDIUM. Fix: rewrite the fallback so it does NOT merely drop the row-lock; name the real cross-path counterparties (approve_and_recognize 005:89, attest 009:138, plus reverse_recognition 005:139 and the revrec-insert lineage trigger 005:173 - 5, not 2) and cite the NO ACTION FKs as the durable barrier with the row-lock as a spurious-abort-avoidance optimization.
- **[migration] Positive posture asserts using has_table_privilege(...,'INSERT') return FALSE under column-scoped grants (apparatus, scope_quote).** Evidence: live - granting insert on a column subset yields has_table_privilege=f while has_column_privilege=t. An "etc."-copied table-level assert on apparatus fails the migration on a correct matrix, or pushes a builder to grant table-level INSERT (re-adding status, reopening D2). Fix: write per-column has_column_privilege asserts for column-scoped objects; reserve the table-level idiom for fully-granted relations.
- **[migration] Down-migration DROP ROLE ops_app is blocked by residual granted privileges (schema USAGE, DB CONNECT, table/column/EXECUTE grants), not just ownership.** Evidence: live - `drop role` after granting USAGE+SELECT errors "cannot be dropped because some objects depend on it: privileges for schema ops / table ops.apparatus". A down that forgets USAGE/CONNECT/EXECUTE leaves ops_test half-broken, failing the reversible up/down/up ladder. Fix: revoke every up-grant in reverse before DROP ROLE, or use `DROP OWNED BY ops_app` (which also drops the privileges) then DROP ROLE as the robust idempotent teardown.
- **[cutover] Env-var naming is internally contradictory (Section 7 rotate-OPS_DEV_DSN vs Section 8/AC6 OPS_APP_DSN vs OPS_DEV_ADMIN_DSN).** Evidence: three names in play; the app reads only os.environ['OPS_DEV_DSN'], the smoke script only process.env.OPS_DEV_DSN; repo grep for OPS_APP_DSN/OPS_DEV_ADMIN_DSN = 0 hits. An implementer following one section breaks the other. Fix: pick one scheme once - keep OPS_DEV_DSN as the app/behavior identity (value=ops_app), add OPS_DEV_ADMIN_DSN for fixtures, drop OPS_APP_DSN (or define it equal and reconcile AC6).
- **[cutover] "Six consumers cut over by one value" is overstated; only 5 code consumers key on OPS_DEV_DSN, the CLI is doc-only.** Evidence: the only OPS_DEV_DSN reference inside packages/ops-intake is tests/conftest.py; approve.py/load.py/envelope.py take dsn as an argument. The "documented CLI runs" consumer reads no source; its cutover depends on how operators invoke it (env vs explicit --dsn), which the spec does not pin - risking an operator still running the CLI as postgres post-cutover. Fix: enumerate the actual CLI entrypoint(s) and how they resolve the DSN; reframe as "5 code consumers keyed on OPS_DEV_DSN + 1 runbook convention" and add a runbook edit if the CLI takes a flag.

### LOW
- **[grant-matrix] ops.persons SELECT is an unnecessary over-grant and its note misstates the mechanism.** Evidence: no ops_app-executed path reads persons directly (FK RI runs as constraint owner; the persons existence read lives inside the DEFINER attest fn). Fix: drop the row, or correct the note to "precautionary read; not required for FK validation (RI runs as owner) nor the DEFINER fns (owner-run)".
- **[grant-matrix] Apparatus column-scoped INSERT grant is under-specified as "all load.py cols EXCEPT status".** Evidence: post-D2 insert_apparatus names exactly 11 columns; a column-scoped INSERT denies any unlisted column, and superuser bypass hides an omission until DSN cutover. Fix: pin the literal 11-column list verbatim and add positive has_column_privilege asserts (e.g. quote_line_id, equipment_model_ref, provenance_status) so a missed column fails the migration, not the live pipeline.
- **[boundary] Sec-4 rationale for scope_quote UPDATE(total_quoted_hours) omits the cascade-DELETE trigger path.** Evidence: trg_scope_quote_line_hours is AFTER INSERT OR DELETE OR UPDATE and fires as ops_app during the approve.py:56 full-replacement cascade DELETE. Grant is present (no hole); the rationale names only INSERT/freeze, so a future "tightening" to INSERT-only reasoning would break the most-exercised runtime path. Fix: amend the note to cover INSERT, UPDATE, AND cascade-DELETE, and add a re-materialize green assertion.
- **[concurrency] Task-0 spike is a single-session probe elevated to a concurrency proof (permanent regression test_012).** Evidence: Section 0 is one `set local role` + one `select ... for update of a` + rollback; a single non-contended session cannot surface a two-session interleave. ADJUDICATION (MEDIUM->LOW): softened because the NO ACTION FK backstop makes the untested interleave fail-closed, so the row-lock is a clean-failure/perf optimization, not the sole corruption barrier. Fix: split the gate - keep the privilege probe, and add a separate two-session regression (session A holds approve_run mid-txn post-apparatus-lock; session B invokes approve_and_recognize; assert B blocks until A commits).
- **[concurrency] Probe's inline comment "FOR UPDATE also needs SELECT on read cols" mis-scopes WHY SELECT is needed.** Evidence: the matrix uses table-level SELECT; the probe is faithful but the comment could mislead a builder into column-scoping SELECT and breaking FOR UPDATE. Fix: note that FOR UPDATE relies on TABLE-level SELECT and column-scoping apparatus/scopes SELECT is out of scope.
- **[boundary/missed] revenue_recognition_event SELECT-only rationale omits three INVOKER protect_recognition triggers.** Evidence (lens-missed, same class as the scope_quote LOW): trg_apparatus/project/scope_protect_recognition each run `select coalesce(sum(recognized_amount)...) from ops.revenue_recognition_event` as ops_app on cancel/deactivate UPDATEs; the Sec-4 note cites only "approve_run reads for conflict checks". Grant present, rationale incomplete -> tightening would break an INVOKER-trigger path on the more security-sensitive revenue table. Fix: extend the SELECT-only rationale to name the three protect_recognition triggers.
- **[migration] has_function_privilege `(...)` placeholder and unqualified overloaded names error out.** Evidence: live `has_function_privilege('public','ops.issue_billing_application','EXECUTE')` -> "expected a left parenthesis"; issue_billing_application has 2 overloads. Fails-loud. Fix: replace `(...)` with the exact arg-type signature in every has_function_privilege/ALTER FUNCTION statement; enumerate both issue_billing_application overloads.

### INFO
- **[grant-matrix] R2 view-security resolved in the spec's favor.** Downgrade R2 from open risk to a one-line in-migration assertion that the 11 ops views stay postgres-owned and non-security_invoker, so a future redefinition cannot silently require withheld base-table grants.
- **[boundary] approve_and_recognize (and reverse_recognition) lack the p_actor_person_id existence guard their sibling fns have.** Not a boundary escalation and fully bounded by RI (actor_person_id is NOT NULL + FK to ops.persons), so residual is only error-message consistency. Fix: note in "carried risks"; optionally add the guard during the DEFINER conversion since the functions are being touched.
- **[migration] Down re-GRANT EXECUTE TO PUBLIC must cover all 35 functions, not only the 9 converted, for a clean up/down/up round-trip.** Fix: down `GRANT EXECUTE ON ALL FUNCTIONS IN SCHEMA ops, core[, work if present] TO PUBLIC`, inheriting the same work-absent presence-gate as the CRITICAL finding.

### Additional gaps folded from verification.missed (not in any lens's own findings)
- **[migration/missed - portability, ~HIGH] REVOKE CONNECT is not authored-portable.** `revoke connect on database current_database()` is a syntax error and a bare `current_database` parses as a literal db name; since the one 012 runs on two differently-named DBs (ops_test, ops_dev), it must use dynamic SQL: `EXECUTE format('revoke connect on database %I from public', current_database())`. The angle-bracket notation hides a real defect. Operator should weigh whether to elevate this above INFO.
- **[cutover/missed - CRITICAL-adjacent] The spec's two-bucket framing (ladder+TRUNCATE=admin, everything else=ops_app) is missing a THIRD admin bucket: setup DML.** person_id and the eligible fixtures INSERT ops.persons (matrix: SELECT-only) and status-bearing apparatus - both admin-only. Even a correct DSN split still fails without routing these setup INSERTs to admin.
- **[cutover/missed] AC5 conflation.** The recognition wrapper/route tests exercise the DEFINER fns over pre-seeded (admin-set) apparatus; they never drive apparatus creation through approve_run/load.py AS ops_app, so they prove EXECUTE-on-recognition-fns but NOT the column-scoped INSERT/UPDATE grants. The spec must name which harness carries the intake-and-approve-as-ops_app leg that actually validates the column-scoped matrix.
- **[concurrency/missed] The recognized-then-reapprove edge is untested.** ops_app has DELETE on ops.scopes but the NO ACTION FK from revenue_recognition_event means a full-replacement approve on a project with a recognized apparatus hard-fails at cascade time (same under ops_app and superuser). Boundary tests should cover the recognized-then-reapprove path, not just the empty-project path (at least INFO).
- **[migration/missed] Second-up idempotency is unverified beyond the role-create DO block.** Because ADP records nothing for functions, the reversibility AC should assert the second up reaches the identical catalog state, not merely that it does not error.

## 4. Refuted / false-alarm notes (brief)
- **"Silent revenue corruption" from dropping the apparatus row-lock (task0-concurrency HIGH).** Refuted as corruption: the NO ACTION FK (revenue_recognition_event/completion_attestation.apparatus_id -> ops.apparatus) plus fresh-UUID reinsert make the race fail-closed (txn abort), so severity was adjusted HIGH->MEDIUM. The spec mischaracterization is real; the corruption consequence is not.
- **"ops_app has no source privilege" (cutover CRITICAL #2 secondary reason).** Refuted: the matrix grants apparatus INSERT on all load.py cols except status, and load.py's INSERT includes source, so source-INSERT is held. The denial is status-only; the finding stands at CRITICAL on the status ground alone.
- **Task-0 spike SELECT list "understates the FOR UPDATE probe" (boundary LOW).** Adjusted to INFO: scope_quote SELECT is already in the Sec-4 matrix and Sec-8's full pipeline exercises _freeze, so there is no grant gap - pure wording/precision with an existing compensating test.
- **No missed grant-matrix gap on re-ground:** every ops-intake DML statement, all 4 FOR UPDATE sites, the 4 EXECUTE grants, and the scopes-DELETE cascade are covered; no statement targets a "(none)" table. The matrix's single-role posture is intact.

## 5. Genuine operator decisions surfaced by the review
- Whether to DROP the ops.persons SELECT grant entirely (tightest least-privilege) or KEEP it as a corrected precautionary read. Both are defensible; least-privilege thesis favors dropping.
- Whether to elevate the REVOKE CONNECT portability defect (missed item) above INFO given it, like the `work`-schema CRITICAL, breaks the one-ladder-two-DBs invariant.
- The env-var scheme to standardize on (recommended: keep OPS_DEV_DSN=ops_app for behavior, add OPS_DEV_ADMIN_DSN for fixtures, drop OPS_APP_DSN) - a naming choice the spec must make once and propagate to Section 8 + AC6.
